# Lời giải bài tập nền tảng

Đây là model solution. Thiết kế production có thể khác nếu invariant và trade-off được nêu rõ.

## Level 1 — Nhớ và giải thích

1. Server là PostgreSQL instance; database là logical database được connection chọn; schema là namespace bên trong database; table là relation chứa rows và columns.
2. DBMS cung cấp query processing, constraints, transactions, concurrency control, indexes, permissions, durability và recovery.
3. Projection chọn output expression; predicate chọn row; ordering định nghĩa result order; pagination trả về một slice có giới hạn của một order xác định.
4. Relation mặc định không có thứ tự, nên limit không kèm ordering không xác định một tập row ổn định.
5. Ví dụ: primary key định danh row; foreign key bảo vệ relationship; `NOT NULL` ngăn value bắt buộc bị thiếu; `CHECK` giới hạn state được phép; `UNIQUE` ngăn identity trùng.
6. `DELETE` xóa row và có thể dùng predicate; `TRUNCATE` xóa toàn bộ row bằng relation-level operation; `DROP TABLE` xóa table definition và data.
7. `COMMIT` hoàn tất transaction; `ROLLBACK` loại bỏ các change của nó.
8. `NULL` biểu diễn dữ liệu missing/unknown/not-applicable, còn empty string là một string value đã biết nhưng rỗng.

## Level 2 — Áp dụng

### 1. Price range

~~~sql
SELECT product_id, product_name, unit_price
FROM sales.products
WHERE active = TRUE
  AND unit_price BETWEEN 50 AND 150
ORDER BY unit_price DESC, product_id;
~~~

### 2. Order mới nhất của customer 8

~~~sql
SELECT order_id, order_status, ordered_at
FROM sales.orders
WHERE customer_id = 8
ORDER BY ordered_at DESC, order_id DESC
LIMIT 5;
~~~

### 3. Order total

~~~sql
SELECT
    order_id,
    round(sum(quantity * unit_price * (1 - discount_pct / 100)), 2) AS order_total
FROM sales.order_items
GROUP BY order_id
ORDER BY order_id;
~~~

### 4. Customer chưa có order

~~~sql
SELECT c.customer_id, c.full_name
FROM sales.customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM sales.orders AS o
    WHERE o.customer_id = c.customer_id
);
~~~

### 5. Shipment events

~~~sql
CREATE TABLE lab.shipment_events (
    shipment_event_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales.orders(order_id),
    event_type TEXT NOT NULL CHECK (event_type IN ('created', 'packed', 'shipped')),
    event_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (order_id, event_type)
);
~~~

### 6. Insert event idempotent

~~~sql
INSERT INTO lab.shipment_events (order_id, event_type)
VALUES (1001, 'packed')
ON CONFLICT (order_id, event_type) DO NOTHING;
~~~

Unique constraint tạo ra idempotency boundary có authority ở database.

### 7. Transaction

~~~sql
BEGIN;

INSERT INTO sales.order_items (order_id, product_id, quantity, unit_price)
VALUES (1012, 3, 1, 249.99);

UPDATE sales.orders
SET order_status = 'paid'
WHERE order_id = 1012
  AND order_status = 'pending';

-- Kiểm tra affected-row count trong application code.
COMMIT;
~~~

Nếu insert hoặc update fail, rollback toàn bộ transaction. Nếu update ảnh hưởng zero row, service phải quyết định order đã paid, không còn pending hay không tồn tại.

### 8. Kết quả `NULL`

~~~text
NULL = NULL   -> UNKNOWN
NULL IS NULL  -> TRUE
NULL <> 'VN'  -> UNKNOWN
~~~

Chỉ kết quả `IS NULL` pass một `WHERE` clause.

## Level 3 — Engineering

1. Dùng atomic conditional update như `UPDATE inventory SET available = available - :qty WHERE product_id = :id AND available >= :qty`, rồi kiểm tra affected-row count trong transaction. Có thể lock row hoặc dùng serializable isolation kèm retry. Mấu chốt là check và write phải trở thành một operation do database kiểm soát.
2. Dùng stable cursor: `WHERE (ordered_at, order_id) < (:last_ordered_at, :last_order_id) ORDER BY ordered_at DESC, order_id DESC LIMIT 50`. Thêm index bắt đầu bằng `(ordered_at DESC, order_id DESC)` hoặc ordering tương thích. Verify plan.
3. Thêm column nullable hoặc safe default ở expand phase, backfill theo batch có giới hạn, deploy code bắt đầu ghi value, validate, sau đó enforce `NOT NULL` ở contract phase. Monitor lock, replication lag, write latency và tiến độ backfill.
4. Hai request có thể cùng thấy “không có row” trước khi request nào insert. Thêm `UNIQUE` constraint/index trên canonicalized email và xử lý unique violation hoặc kết quả `ON CONFLICT`.
5. Thay thế như vậy phá distinction giữa unknown và literal text đã biết, làm khó việc sửa dữ liệu sau này và thay đổi semantics của `IS NULL`/`COUNT`. Giữ `NULL` khi nó có meaning; dùng display fallback ở presentation boundary.

## Lời giải debugging challenges

1. Thêm unique tie-breaker: `ORDER BY ordered_at DESC, order_id DESC`. Với offset lớn, ưu tiên keyset pagination.
2. Dùng `WHERE country IS NULL`.
3. Check và insert không atomic. Enforce unique constraint rồi dùng `INSERT ... ON CONFLICT` hoặc bắt uniqueness error.
4. Bọc hai statement trong một transaction và rollback khi có failure.
5. Statement không có `WHERE`. Preview bằng `SELECT`, thêm predicate, dùng transaction và verify affected-row count.
