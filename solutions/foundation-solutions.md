# Foundation Exercise Solutions

These are model solutions. Production designs may vary when their invariants and trade-offs are explicit.

## Level 1 — Recall

1. A server is the PostgreSQL instance; a database is a logical database selected by a connection; a schema is a namespace inside it; a table is a relation containing rows and columns.
2. A DBMS provides query processing, constraints, transactions, concurrency control, indexes, permissions, durability and recovery.
3. Projection selects output expressions; a predicate selects rows; ordering defines result order; pagination returns a bounded slice of a deterministic order.
4. Relations are unordered by default, so a limit without ordering does not identify a stable set of rows.
5. Examples: primary key identifies a row; foreign key protects a relationship; `NOT NULL` prevents missing required values; `CHECK` restricts allowed states; `UNIQUE` prevents duplicate identities.
6. `DELETE` removes rows and can use a predicate; `TRUNCATE` removes all rows using a relation-level operation; `DROP TABLE` removes the table definition and data.
7. `COMMIT` completes the transaction; `ROLLBACK` abandons its changes.
8. `NULL` represents missing/unknown/not-applicable data, while an empty string is a known string value.

## Level 2 — Apply

### 1. Price range

```sql
SELECT product_id, product_name, unit_price
FROM sales.products
WHERE active = TRUE
  AND unit_price BETWEEN 50 AND 150
ORDER BY unit_price DESC, product_id;
```

### 2. Newest orders for customer 8

```sql
SELECT order_id, order_status, ordered_at
FROM sales.orders
WHERE customer_id = 8
ORDER BY ordered_at DESC, order_id DESC
LIMIT 5;
```

### 3. Order totals

```sql
SELECT
    order_id,
    round(sum(quantity * unit_price * (1 - discount_pct / 100)), 2) AS order_total
FROM sales.order_items
GROUP BY order_id
ORDER BY order_id;
```

### 4. Customers without orders

```sql
SELECT c.customer_id, c.full_name
FROM sales.customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM sales.orders AS o
    WHERE o.customer_id = c.customer_id
);
```

### 5. Shipment events

```sql
CREATE TABLE lab.shipment_events (
    shipment_event_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales.orders(order_id),
    event_type TEXT NOT NULL CHECK (event_type IN ('created', 'packed', 'shipped')),
    event_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (order_id, event_type)
);
```

### 6. Idempotent event insertion

```sql
INSERT INTO lab.shipment_events (order_id, event_type)
VALUES (1001, 'packed')
ON CONFLICT (order_id, event_type) DO NOTHING;
```

The unique constraint gives the database an authoritative idempotency boundary.

### 7. Transaction

```sql
BEGIN;

INSERT INTO sales.order_items (order_id, product_id, quantity, unit_price)
VALUES (1012, 3, 1, 249.99);

UPDATE sales.orders
SET order_status = 'paid'
WHERE order_id = 1012
  AND order_status = 'pending';

-- Check the affected-row count in application code.
COMMIT;
```

If the insert or update fails, roll back the whole transaction. If the update affects zero rows, the service must decide whether the order was already paid, no longer pending or missing.

### 8. `NULL` outcomes

```text
NULL = NULL   -> UNKNOWN
NULL IS NULL  -> TRUE
NULL <> 'VN'  -> UNKNOWN
```

Only the `IS NULL` result passes a `WHERE` clause.

## Level 3 — Engineering

1. Use an atomic conditional update such as `UPDATE inventory SET available = available - :qty WHERE product_id = :id AND available >= :qty`, then check the affected-row count inside a transaction. Alternatively lock the row or use serializable isolation with retry. The key is that the check and write are one database-controlled operation.
2. Use a stable cursor: `WHERE (ordered_at, order_id) < (:last_ordered_at, :last_order_id) ORDER BY ordered_at DESC, order_id DESC LIMIT 50`. Add an index beginning with `(ordered_at DESC, order_id DESC)` or a compatible ordering. Verify the plan.
3. Add the column nullable or with a safe default in an expand phase, backfill in bounded batches, deploy code that writes the value, validate, then enforce `NOT NULL` in a later contract phase. Monitor locks, replication lag, write latency and backfill progress.
4. Two requests can both observe “no row” before either inserts. Add a `UNIQUE` constraint/index on the canonicalized email representation and handle the unique-violation/`ON CONFLICT` result.
5. The replacement destroys the distinction between unknown and known literal text, complicates future correction and changes `IS NULL`/`COUNT` semantics. Keep `NULL` when it carries meaning and apply display fallback at the presentation boundary.

## Debugging challenges

1. Add a unique tie-breaker: `ORDER BY ordered_at DESC, order_id DESC`. For high offsets prefer keyset pagination.
2. Use `WHERE country IS NULL`.
3. The check and insert are not atomic. Enforce a unique constraint and use `INSERT ... ON CONFLICT` or catch the uniqueness error.
4. Wrap both statements in one transaction and roll back on failure.
5. The statement has no `WHERE` clause. Preview with `SELECT`, add a predicate, use a transaction and verify the affected-row count.
