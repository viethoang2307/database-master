# Lesson 3 — DDL, Data Types and Constraints

## Lesson overview

Data Definition Language changes database structure. The transcript presents `CREATE`, `ALTER` and `DROP`; this lesson adds the design question behind those commands: what states should the database permit?

### Learning objectives

- Choose practical PostgreSQL types for identifiers, money-like values, dates and timestamps.
- Design primary keys and foreign keys for the sales schema.
- Explain `NOT NULL`, `UNIQUE`, `CHECK` and referential integrity.
- Predict which constraints reject an invalid write.
- Distinguish `DELETE`, `TRUNCATE` and `DROP`.

## Intuition and formal model

A schema is an executable contract. A constraint is a predicate that every stored row or relationship must satisfy. Constraints solve the problem of invalid state being created by a new code path, a retry, a batch job or concurrent writer.

Examples from the lab:

- `sales.customers.customer_id` is the row identity.
- `sales.orders.customer_id` references an existing customer.
- `sales.order_items.quantity > 0` prevents nonsensical inventory quantities.
- `sales.customers.email` is unique because the application treats it as a natural identity.

## Data type decisions

| Requirement | PostgreSQL choice | Reason |
| --- | --- | --- |
| Generated numeric identifier | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Database-generated value with explicit-value flexibility for imports. |
| Currency-like exact arithmetic | `NUMERIC(12, 2)` | Exact decimal arithmetic; avoid floating point for monetary values. |
| Instant in time | `TIMESTAMPTZ` | Stores an instant and displays it in the session time zone. |
| Calendar date without time | `DATE` | Avoids inventing a time zone for a date-only business fact. |
| Boolean state | `BOOLEAN` | More expressive than integer flags. |
| Unbounded human text | `TEXT` | Add a length constraint only when it expresses a real rule. |

The correct type is part of correctness. “Store everything as text and validate later” moves data-quality work to every consumer and makes indexing/comparison less reliable.

## Example: a constrained table

```sql
CREATE TABLE lab.inventory_reservations (
    reservation_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales.orders(order_id),
    product_id BIGINT NOT NULL REFERENCES sales.products(product_id),
    reserved_quantity INTEGER NOT NULL CHECK (reserved_quantity > 0),
    status TEXT NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'released', 'fulfilled')),
    UNIQUE (order_id, product_id)
);
```

Expected behavior:

- A missing `order_id` fails `NOT NULL`.
- An unknown order fails the foreign key.
- Zero quantity fails the `CHECK`.
- A repeated `(order_id, product_id)` fails the composite uniqueness rule.

PostgreSQL automatically creates indexes to enforce primary key and unique constraints. A foreign key enforces relationship validity, but PostgreSQL does not automatically create an index on the referencing column; add one when the workload needs efficient parent updates/deletes or child lookups.

## Internal behavior

DDL updates PostgreSQL catalogs. A primary key/unique constraint has an enforcement index. A foreign key causes PostgreSQL to check referenced keys and coordinate relevant writes. Adding a constraint to existing data may scan or validate rows, so production migrations must consider lock duration and data cleanup.

## Comparison: `DELETE`, `TRUNCATE`, `DROP`

| Statement | Purpose | Internal behavior | Performance | Typical use |
| --- | --- | --- | --- | --- |
| `DELETE` | Remove selected rows | Row-level DML with predicates and triggers | Can be expensive for many rows; produces dead tuples in PostgreSQL | Business deletion or selective cleanup |
| `TRUNCATE` | Remove all rows from a table | Fast relation-level operation; can restart identity and cascade | Usually faster for full reset; stronger locking semantics | Disposable staging/lab data |
| `DROP TABLE` | Remove table definition and data | Removes the relation and dependent objects when cascaded | Fast but destructive | Schema teardown/migration |

All three are transactional in PostgreSQL, but “transactional” does not mean “safe to run casually in production.” Always scope the target and migration carefully.

## Performance and production notes

- Every index that supports a constraint consumes storage and write maintenance work.
- A wide natural key can make all referencing indexes and joins larger; surrogate keys do not remove the need for a unique business key when one exists.
- `CHECK` constraints should encode stable invariants, not rapidly changing business workflows.
- Schema changes should be versioned migrations, reviewed and observable; do not let an application silently create production tables at startup.

## ORM perspective

JPA annotations such as `@Id`, `@Column(nullable = false)`, `@UniqueConstraint` and `@ManyToOne` describe mappings and may generate DDL in development. In production, use explicit migrations and verify the resulting PostgreSQL constraints with catalog queries.

## Mental models

- A constraint is an executable invariant, not merely documentation.
- A primary key identifies a row; it does not automatically model every business uniqueness rule.
- Foreign keys protect relationships, while indexes determine whether common relationship operations are efficient.

## Interview questions

1. **Junior — What is the difference between a primary key and a unique constraint?**  A table has at most one primary key, which identifies rows and is implicitly `NOT NULL`; it may have multiple unique constraints for other identities.
2. **Junior — Does a foreign key automatically create an index in PostgreSQL?**  No. The referenced key has an enforcement index, but the referencing column may need an explicit index for workload performance.
3. **Mid — Why use `NUMERIC` for money?**  It provides exact decimal arithmetic, avoiding many binary floating-point representation surprises.
4. **Mid — When is `TRUNCATE` preferable to `DELETE`?**  When the intention is to remove all rows from a disposable/staging relation and its stronger locking/identity behavior is acceptable.
5. **Senior — How can adding a constraint affect a production deployment?**  Validation and catalog changes can scan data or acquire locks; migration design must account for existing violations, lock duration and rollout order.
