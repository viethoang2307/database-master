# Lesson 3 — DDL, Data Types và Constraints

## Tổng quan lesson

Data Definition Language thay đổi cấu trúc database. Transcript trình bày `CREATE`, `ALTER` và `DROP`; lesson này bổ sung câu hỏi thiết kế phía sau các command đó: database nên cho phép những state nào?

### Mục tiêu học tập

- Chọn PostgreSQL type thực tế cho identifier, giá trị kiểu money, date và timestamp.
- Thiết kế primary key và foreign key cho sales schema.
- Giải thích `NOT NULL`, `UNIQUE`, `CHECK` và referential integrity.
- Dự đoán constraint nào sẽ reject một write không hợp lệ.
- Phân biệt `DELETE`, `TRUNCATE` và `DROP`.

## Trực giác và formal model

Schema là executable contract. Constraint là predicate mà mọi stored row hoặc relationship phải thỏa mãn. Constraint giải quyết vấn đề invalid state có thể được tạo bởi code path mới, retry, batch job hoặc concurrent writer.

Ví dụ trong lab:

- `sales.customers.customer_id` là identity của row.
- `sales.orders.customer_id` tham chiếu đến một customer tồn tại.
- `sales.order_items.quantity > 0` ngăn quantity inventory vô nghĩa.
- `sales.customers.email` là unique vì application xem nó là natural identity.

## Quyết định data type

| Requirement | Lựa chọn PostgreSQL | Lý do |
| --- | --- | --- |
| Numeric identifier tự sinh | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Database sinh value nhưng vẫn cho phép explicit value khi import. |
| Exact arithmetic kiểu tiền tệ | `NUMERIC(12, 2)` | Exact decimal arithmetic; tránh floating point cho monetary value. |
| Một instant trong thời gian | `TIMESTAMPTZ` | Lưu một instant và hiển thị theo session time zone. |
| Calendar date không có time | `DATE` | Không tự tạo time zone cho business fact chỉ có ngày. |
| Boolean state | `BOOLEAN` | Diễn đạt rõ hơn integer flag. |
| Human text không giới hạn cố định | `TEXT` | Chỉ thêm length constraint khi nó biểu đạt một rule thực tế. |

Chọn đúng type là một phần của correctness. “Lưu mọi thứ thành text rồi validate sau” đẩy data-quality work sang mọi consumer và làm indexing/comparison kém tin cậy hơn.

## Ví dụ: table có constraint

~~~sql
CREATE TABLE lab.inventory_reservations (
    reservation_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales.orders(order_id),
    product_id BIGINT NOT NULL REFERENCES sales.products(product_id),
    reserved_quantity INTEGER NOT NULL CHECK (reserved_quantity > 0),
    status TEXT NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'released', 'fulfilled')),
    UNIQUE (order_id, product_id)
);
~~~

Hành vi kỳ vọng:

- Thiếu `order_id` sẽ fail `NOT NULL`.
- Order không tồn tại sẽ fail foreign key.
- Quantity bằng zero sẽ fail `CHECK`.
- Cặp `(order_id, product_id)` lặp lại sẽ fail composite uniqueness rule.

PostgreSQL tự tạo index để enforce primary key và unique constraint. Foreign key enforce relationship validity, nhưng PostgreSQL không tự động tạo index trên referencing column; hãy thêm index khi workload cần parent update/delete hoặc child lookup hiệu quả.

## Hành vi bên trong

DDL cập nhật PostgreSQL catalog. Primary key/unique constraint có enforcement index. Foreign key khiến PostgreSQL kiểm tra referenced key và điều phối các write liên quan. Thêm constraint vào data đã tồn tại có thể phải scan hoặc validate row, vì vậy production migration phải tính đến lock duration và việc dọn dữ liệu trước đó.

## So sánh: `DELETE`, `TRUNCATE`, `DROP TABLE`

| Statement | Mục đích | Hành vi bên trong | Performance | Use case điển hình |
| --- | --- | --- | --- | --- |
| `DELETE` | Xóa row được chọn | Row-level DML với predicate và trigger | Có thể đắt với nhiều row; tạo dead tuple trong PostgreSQL | Business deletion hoặc selective cleanup |
| `TRUNCATE` | Xóa toàn bộ row của table | Fast relation-level operation; có thể restart identity và cascade | Thường nhanh hơn để reset toàn bộ; locking semantics mạnh hơn | Staging/lab data có thể bỏ |
| `DROP TABLE` | Xóa table definition và data | Xóa relation và dependent object khi dùng cascade | Nhanh nhưng destructive | Schema teardown/migration |

Cả ba đều transactional trong PostgreSQL, nhưng “transactional” không có nghĩa là có thể chạy tùy tiện trong production. Luôn scope target và migration thật cẩn thận.

## Performance và production notes

- Mỗi index phục vụ constraint tiêu tốn storage và write-maintenance work.
- Natural key rộng làm các referencing index và join lớn hơn; surrogate key không loại bỏ nhu cầu có unique business key nếu business có rule đó.
- `CHECK` nên encode invariant ổn định, không phải workflow business thay đổi liên tục.
- Schema change nên là versioned migration, được review và observable; không để application âm thầm tạo production table khi startup.

## Góc nhìn ORM

JPA annotation như `@Id`, `@Column(nullable = false)`, `@UniqueConstraint` và `@ManyToOne` mô tả mapping và có thể generate DDL trong development. Trong production, hãy dùng explicit migration và verify constraint PostgreSQL thực tế bằng catalog query.

## Mental models

- Constraint là executable invariant, không chỉ là documentation.
- Primary key định danh row; nó không tự mô hình hóa mọi business uniqueness rule.
- Foreign key bảo vệ relationship, còn index quyết định các operation trên relationship phổ biến có hiệu quả hay không.

## Câu hỏi phỏng vấn

1. **Junior — Primary key khác unique constraint như thế nào?** Một table có tối đa một primary key, dùng để định danh row và mặc nhiên `NOT NULL`; table có thể có nhiều unique constraint cho các identity khác.
2. **Junior — Foreign key trong PostgreSQL có tự tạo index không?** Không. Referenced key có enforcement index, nhưng referencing column có thể cần explicit index cho workload.
3. **Mid — Vì sao dùng `NUMERIC` cho money?** Nó cung cấp exact decimal arithmetic, tránh nhiều bất ngờ do binary floating-point representation.
4. **Mid — Khi nào `TRUNCATE` phù hợp hơn `DELETE`?** Khi mục tiêu là xóa toàn bộ row của disposable/staging relation và locking/id­entity behavior mạnh hơn vẫn chấp nhận được.
5. **Senior — Thêm constraint ảnh hưởng production deployment như thế nào?** Validation và catalog change có thể scan data hoặc acquire lock; migration phải tính đến violation hiện có, lock duration và rollout order.
